# ClaudeCodeSkills — скиллы для разработки и оценки пакетов Vortex

Набор скиллов для [Claude Code](https://docs.claude.com/claude-code) — CLI-агента от Anthropic. Скиллы автоматизируют типовые операции вокруг Vortex: определение архитектурного слоя для новой системы, проектирование новых пакетов по канону, оформление ТЗ, послойную сборку кода по ТЗ и оценку кода по двум осям — **формы** (метрики/паттерны) и **поведения** (прочность логических нитей).

Папка содержит **исходные тексты** скиллов. Чтобы Claude Code их использовал, скиллы нужно скопировать в одну из стандартных директорий — см. раздел «Установка».

## Состав

| Скилл | Назначение | Триггеры |
|-------|-----------|----------|
| [vortex-layer-detect](vortex-layer-detect/SKILL.md) | Определение архитектурного слоя (1/2/3) для новой системы Vortex до генерации кода | «сделаем систему X», «добавим подсистему Y», «хочу пакет для Z» в контексте Vortex |
| [vortex-initial-architecture](vortex-initial-architecture/SKILL.md) | Проектирование первичной архитектуры пакета Vortex по каноническому алгоритму (Stage 0 + 7 шагов) | «спроектируй архитектуру», «сформируй структуру пакета», «набросай каркас системы X» |
| [code-quality](code-quality/SKILL.md) | Жёсткая оценка **формы** Unity-кода по формулам с архитектурным множителем. 4 ветки по объёму (≤3000 LOC / 3000–12000 / частичный / субъективный) | «оцени качество кода», «прогони по критериям оценки», «проверь пакет на качество» |
| [applied-quality](applied-quality/SKILL.md) | Оценка **прикладного** качества (поведения) по канону «Сценарная прочность»: трассировка логических нитей вход→выход, спутанность, ступенчатость, рекурсия (потолок катастроф). 3 ветки по объёму (моно ≤2000 / шардинг с реконструкцией графа 2000–10000 / частичный) | «оцени корректность пакета», «проверь систему на логичность / адекватность / правильность», «где порвётся на практике» |
| [tz-design](tz-design/SKILL.md) | Оформление технического задания (ТЗ) на новую фичу/подсистему или self-audit готового ТЗ. Двухуровневая структура документа, калибровка по целевой зрелости. Для систем с внешним входом или защитной ролью — модель угроз и граница доводки (раздел 6а ТЗ) | «оформи как ТЗ», «сделай ТЗ», «напиши техническое задание», «проанализируй ТЗ», «оцени ТЗ на полноту» |
| [tz-build](tz-build/SKILL.md) | Послойная сборка кода пакета по закрытому ТЗ: 9 итераций от примитивов к основной логике, каждая точка подтверждения — стоп, отклонения от канона — только с согласия пользователя. После каждой итерации — компиляция и оценка одним агентом (форма или applied-quality). Ведёт журнал сборки | «собери код по ТЗ», «собирай пакет по ТЗ», «реализуй ТЗ», «послойная сборка» |

## Когда какой скилл применять

```
Новая система в Vortex
  └─► vortex-layer-detect           (определить слой)
        └─► vortex-initial-architecture  (спроектировать пакет)
              └─► tz-design             (оформить ТЗ, закрыть открытые вопросы)
                    └─► tz-build              (собрать код по ТЗ итерациями; внутри — оценки по итерациям)
                          ├─► code-quality      (оценить ФОРМУ: метрики, паттерны, связность — код «в покое»)
                          └─► applied-quality   (оценить ПОВЕДЕНИЕ: нити вход→выход, спутанность, рекурсия — код «в движении»)
```

- **vortex-layer-detect** — первый шаг при добавлении любой новой системы. MUST run до генерации кода.
- **vortex-initial-architecture** — после определения слоя. Вырабатывает структуру (шина, конфиг, контроллер, модель, пресеты, интерфейс, представления).
- **code-quality** — после реализации (или для аудита). Оценивает **форму** кода: метрики, структуру, паттерны, связность. Балл по 10-балльной шкале с разбором архитектурных дефектов.
- **applied-quality** — после реализации (или для аудита). Оценивает **поведение** кода: прочность логических нитей вход→выход, ступенчатость, спутанность нитей и рекурсию (потолок катастроф). Доказательства — **сценарии отказа** (что рвётся на re-entry/сбое/гонке), а не абстрактные счётчики.
- **tz-design** — оформление ТЗ на фичу/подсистему или аудит готового ТЗ. Может применяться и отдельно от код-флоу; для сборки кода ТЗ должно быть закрыто (без открытых вопросов). Для систем, которые принимают внешний вход или служат защитой (allow-list, авторизация, фильтр), ТЗ фиксирует модель угроз: источники входа, цену ошибки, направление безопасного отказа, поддерживаемые классы входа и «вне модели», платформенные допущения и **границу доводки** — критерий «достаточно» для оценок после реализации.
- **tz-build** — сборка кода по закрытому ТЗ. Не запускается при открытых вопросах в ТЗ (→ tz-design). Если слой не определён: проект на Vortex → vortex-layer-detect, иначе скилл предлагает сепарацию слоёв на утверждение. Идёт 9 итерациями: абстракции (классы/структуры, затем интерфейсы) → модели → пресеты → логика изменения моделей → редакторный сахар → шины и тонкие контроллеры → основная логика → доводка. Перед итерацией — поиск образцов в README/XML-документации (по типам итерации и по требованиям ТЗ к их поведению), список отклонений от канона и таблица типов на подтверждение; гибридные типы (данные + логика) размещаются в самой поздней из своих итераций после подтверждения гибридности. После итерации — компиляция и оценка (форма — для итераций без динамики, applied-quality — с динамикой; в доводке — оба скилла по всему пакету); находки группируются по корневым решениям, повторяющиеся — повод пересмотреть решение, а не латать. Если в ТЗ есть модель угроз (раздел 6а), находки о входе за её границей понижаются до Minor и переход не блокируют; находка, показывающая неверную границу, ведёт к правке модели в ТЗ. Жёсткий режим: ответ пользователя не предсказывается, молчание и «ок» — не согласие. Ответы на пробелы канона копятся в памятке принципов (`<папка сборки>\BuildDocs\architecture-principles.md`); состояние, одобренные отклонения и итоги оценок — в журнале сборки (`<папка сборки>\BuildDocs\<Пакет>_build.md`), по нему сборка продолжается в новой сессии. Папка сборки запрашивается один раз на проект и хранится в памяти проекта.

### code-quality ↔ applied-quality — близнецы, разные оси

Меряют **разное** и не дублируют друг друга:

| | code-quality | applied-quality |
|---|---|---|
| Ось | **форма** (код в покое) | **поведение** (код в движении) |
| Метод | детерминированный (метрики/формулы) | семантический (трассировка нитей вход→выход) |
| Ловит | Fat Interface, DIT, аллокации, дубли | dangling-ссылки, гонки, утечки на re-entry, over-fetch, ступенчатость, рекурсию |

Триггеры близнецов **похожи**, поэтому оба скилла на старте (раздел 0 каждого) **подтверждают направление**: слово «**качество / архитектура / метрики**» → code-quality; «**корректность / логичность / адекватность / правильность / спутанность / что рвётся**» → applied-quality. При неоднозначной формулировке скилл задаёт один уточняющий вопрос до анализа. Полная картина по пакету = прогнать оба.

## Установка

Claude Code загружает скиллы из двух мест:

| Уровень | Путь | Когда использовать |
|---------|------|-------------------|
| User | `~/.claude/skills/<skill-name>/SKILL.md` | На все проекты текущего пользователя |
| Project | `<project-root>/.claude/skills/<skill-name>/SKILL.md` | Только в этом проекте (коммитится в репозиторий) |

**Установка вручную:**

```bash
# User-level (на все проекты)
cp -r Vortex/AITools/ClaudeCodeSkills/vortex-layer-detect ~/.claude/skills/
cp -r Vortex/AITools/ClaudeCodeSkills/vortex-initial-architecture ~/.claude/skills/
cp -r Vortex/AITools/ClaudeCodeSkills/code-quality ~/.claude/skills/
cp -r Vortex/AITools/ClaudeCodeSkills/applied-quality ~/.claude/skills/
cp -r Vortex/AITools/ClaudeCodeSkills/tz-design ~/.claude/skills/
cp -r Vortex/AITools/ClaudeCodeSkills/tz-build ~/.claude/skills/

# Project-level (только в текущем проекте)
mkdir -p .claude/skills
cp -r Vortex/AITools/ClaudeCodeSkills/* .claude/skills/
```

После копирования Claude Code увидит скиллы при следующем запуске. Список активных скиллов доступен через `/skills` в CLI.

## Платформа

Скиллы написаны под **Claude Code** и используют его инструменты (`Agent`, `Bash`, `Grep`, `Read`, `Edit`, `Write`, `Glob`). Соглашения о делегировании — через `subagent_type=Explore`/`general-purpose` с указанием модели (`haiku`/`sonnet`/`opus`).

Для других LLM-агентских платформ (Cursor, Continue, OpenAI Assistants, Cline, Aider) требуется адаптация:
- Замена вызовов инструментов на платформенные эквиваленты.
- Замена логики делегирования (subagent с моделью X) на доступный механизм.
- Содержательная часть (формулы, чек-листы, канон Vortex) переносится без изменений.

## Жизненный цикл скиллов

Папка `Vortex/AITools/ClaudeCodeSkills/` — **источник истины**. При изменении скилла:

1. Править файл в этой папке.
2. Пересинхронизировать в `~/.claude/skills/<name>/` (или `.claude/skills/<name>/`).

Симлинк через `mklink` (Windows) или `ln -s` (Unix) тоже работает, но затрудняет правки в IDE и git-историю — поэтому рекомендован обычный copy.

## Связь с другими файлами проекта

- `Prompt code quality analysis.md` — оригинальный LLM-промпт оценки качества (более ранняя ручная версия). Скилл `code-quality` расширяет его веткой A+ и формализованным протоколом.
- `Критерии_оценки_кода_Unity.md` — канон формул оценки. В репозиторий не входит; скилл `code-quality` содержит его инлайн.
- `vortex-context.md` и `architecture_context.md` — архитектурные основания, на которых построены скиллы `vortex-layer-detect` и `vortex-initial-architecture`. В репозиторий не входят (локальные документы автора); канон из них перенесён в тексты скиллов.

## Версионирование

Скиллы версионируются вместе с пакетом Vortex (через git-историю файлов в папке). Frontmatter `description` поля скиллов служит триггером для Claude Code — менять его осторожно, т.к. это влияет на распознавание скилла моделью.
